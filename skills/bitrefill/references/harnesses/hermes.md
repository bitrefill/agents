# Host: Hermes Agent

> Internal mechanics — never voiced. Speak / think / title tools in plain shopping language: "sign in with your wallet", "approve the payment", "your code is ready"; never x402 / SIWX / JWT / path / endpoint.

The Bitrefill plugin gives Hermes this skill and the Bitrefill connector; its tools arrive as `mcp__bitrefill__<tool>` (`-` → `_`). The connector's sign-in belongs to the Hermes profile owner and is shared by every chat of that profile. Route silently:

1. **Connected** (an `mcp__bitrefill__*` tool in your tool list, or a `bitrefill` server in the deferred-tool catalog: load its tools with `tool_describe` and call them with `tool_call`) → [../touchpoints/mcp.md](../touchpoints/mcp.md). Neither = not connected (the connector is signed out); go to 2, at most one `tool_search` for `bitrefill` first.
2. **Not connected**, `terminal` and `command -v npx` → guest checkout ([../touchpoints/cli.md](../touchpoints/cli.md) § Guest checkout), every call as `npx -y @bitrefill/cli@0.3.0 <command> … --json`, never `npm install -g` or `npm link` (npx keeps its copy in the npm cache), with `--payment_method <method>` last before `--json`; `cart_items` take `package_value` as a string (`[{"product_id":"steam-usa","package_value":"20"}]`). Buy only after a separate `whoami --json` call returns `"identity":"unregistered"` (`&&` checks only its exit code); a signed-in CLI → 3, since the owner keeps it signed out ([../safeguards.md](../safeguards.md) § Hermes). A bare-string result, or `error` / `message` instead of the expected fields, failed, even on exit 0 (the CLI drops `isError`). In a local session, offer "Connect your Bitrefill account" first in the confirm (in a chat app, account purchases happen only on the Hermes machine); if picked, the owner signs in on the Hermes machine ([../touchpoints/mcp.md](../touchpoints/mcp.md) § Hermes Agent), never in chat: never ask for a password, code, key or sign-in address here. Guest `purchase_limit_reached` → offer the connect again, local session only. Hermes never prompts before a `terminal` command, so the confirm is the only gate: call guest `buy-products` only after the user's own reply accepts the quoted product, amount, total, method and email.
3. **Neither**, or the method is rejected → a wallet that pays only x402 runs x402 checkout (below); else send the `https://www.bitrefill.com` product link.

Product, confirm and payment → [grok-bot.md](grok-bot.md) § Product first, one confirm and § Pay; these rules take precedence over it (its no-address line included) and over the wallet pages:

- Crypto: post the amount, network, address (or Lightning invoice) and expiry, as the minutes the invoice gives (`expiration_minutes`), never a computed clock time, and end the turn; check `get-invoice-by-id` once the user says they paid or the wallet's payment went through, never in a waiting loop before the address is out. No address came back → give the invoice id and offer a payment-link checkout, opened with `--return_payment_link true` only after a new yes; never a second order without it. Invoice total above the confirmed one → say so and get a new yes before anyone pays.
- **A wallet the agent has** (any wallet MCP or CLI: Coinbase Wallet MCP, MetaMask, `awal`, Hermes `agent-wallet`… → [../wallets/matrix.md](../wallets/matrix.md)) pays instead of the user, only where checkout is allowed (§ Hermes): quote a coin and network it holds and name the wallet in the confirm; after the yes, open the invoice with `return_payment_link: false` and send the exact `payment_info` amount to its address once; never pay a `payment_link` or open another order through a wallet. The wallet's own approvals and caps apply: when it asks, say "Approve the payment in your wallet" and poll the wallet's own approval status (Coinbase Wallet MCP: `get_request_status`) until it is approved, rejected or the invoice expires; never answer its prompt or raise its cap. Declined, failed, over its cap or unable to pay this invoice → stop: the invoice stays unpaid; post the address so the user can pay by hand; never retry or switch wallet without a new yes. Invoice expired while the wallet request is open → tell the user to reject it and not to pay the old address, and offer a new quote. No wallet → post the address or `payment_link`.
- **A wallet that pays only x402** (no send: AgentCash) can't pay connector or CLI invoices, so paying with it runs the whole order on x402 checkout ([../touchpoints/x402.md](../touchpoints/x402.md) § Path 1) instead of routes 1–2, only where checkout is allowed (§ Hermes), every call through its HTTP tool (AgentCash `fetch` signs in and pays a 402 by itself; Hermes asks before it only when the owner priced it ([../safeguards.md](../safeguards.md) § Hermes), a refusal stopping the order as below, so the confirm and the wallet's caps are the gates; never `scripts/`): `POST /x402/connect` once, then search, `products/detail` and `invoice/create` with its `X-Access-Token` and `maxAmount` `0.01`. Quote `price_usdc`, the wallet and `expires_in_minutes`; after the yes, `POST /x402/invoice/pay` with that `invoice_id` once, `maxAmount` the quoted `price_usdc`, then poll `invoice/status` with the token until `delivery_status` is `all_delivered` (codes in `redemption_info`). Pay refused, failed or above the quote → stop, nothing was bought; offer the product link. 409 → already paid: poll status. Expired → a new invoice, quote and yes; never pay one twice. `/x402/my/*` only in a local session.

## Hermes

- The confirm is the user's reply to your quote with the total; a yes sent before the quote doesn't count, so quote and wait. Only in a local session may an in-chat autonomous opt-in with a spend cap ([../../SKILL.md](../../SKILL.md)) replace it, up to that cap; Hermes still asks per order unless the owner set `trust: full`. After the confirm, call `buy-products` once: Hermes asks the user to approve every order, `/yolo` included, and each answer covers only that order. Never answer that prompt; never suggest **Always**, `/yolo`, `approvals.mode: off` or a higher spend limit; never run `hermes` commands or `manage_connections`, or change Hermes settings. Hermes refused the order (denied, cancelled, timed out, nobody to ask, or a "spend limit was reached" error, Hermes's wording for every refusal) → stop and say "The order wasn't approved, so nothing was bought.", never that a spend limit was reached; never retry, rephrase or switch route. `submit-prepayment-step` and `update-order` raise the same prompt: say "Approve this step in the prompt."; refused → the same stop. Auth error on a connector call → the owner runs `hermes mcp login bitrefill` on the Hermes machine; no guest fallback for that order. Uncertain outcome (`outcome_uncertain` in the tool error) → check `list-invoices` first and tell the user; it never lists unpaid invoices, so nothing there → say the order may exist unpaid and point to the order history on bitrefill.com; never buy again without a new confirm. Autonomous buying (`trust: full` and a higher `spend_limit`, set by the owner) only removes the prompt in a local session; it never makes cron or chat apps buy.
- The connector buys only in a local session (no **Source** line, or Source `Local`): in a chat app Hermes's order prompt goes to whoever is in that chat, who may not be the owner. A chat-app DM is **Source** Telegram, Discord, Slack, WhatsApp (`Whatsapp`, `Whatsapp_Cloud`), Signal, Matrix or Mattermost followed by `("DM with …")` with no `, thread:` (Slack threads every DM, so there it may follow); there the connector only runs `search-products` and `get-product-details` (never balances, invoices, orders or codes), and checkout is guest or x402. Any other Source on those platforms (group, channel, thread): reply only "DM me to finish this". Every other Source (other platforms, webhooks, API server) and cron jobs (Hermes tells you when you run as one): never buy or pay; say "I can't buy from here." A one-shot run looks local; Hermes declines its order prompt itself.
- `terminal` is guest checkout only: never `login`, `verify`, `--payment_method balance` / `cashback`, `--saved_fiat_card_id` or `scripts/`; a wallet CLI only pays an invoice after the confirm; never `execute_code` for Bitrefill or `hermes`; never read `~/.config/bitrefill-cli/` or Hermes token files. Balance, cashback and saved cards only through the connector.
- Codes, `invoice_access_token`, `X-Access-Token` and `payment_link` stay in this chat: never `memory`, files, `cronjob_manage` or `text_to_speech`; never echo the token to the user (Hermes already keeps tool results in its session history). On Hermes, [../safeguards.md](../safeguards.md) § Universal rules' token file doesn't apply, and its in-chat autonomous opt-in applies only as above.

**User hears:** "Searching for [product]…" → "[Product] [amount]: [total] [currency] (≈ $X) by [method]. Confirm?" → connector only: "Approve the order in the prompt." (a guest order has no Hermes prompt; never promise one) → wallet that asks: "Approve the payment in your wallet." → "Send [amount] [coin] on [network] to [address] within [N] minutes" or "Pay here: [link]" → "Your code is ready." / "Done — topped up."
